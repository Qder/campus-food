# 食物规则推荐笔记（campus-food）

> 对照当前代码。本文按**一次请求会调用哪些函数**写，方便对着源码跟。  
> 课设第一版是规则推荐：口味命中率 + 均分 + 销量加权，忌口在 Java 里过滤。每个用户注册时就必须填口味，推荐接口必须登录。

---

## 1. 业务约定

| 环节 | 要求 |
|------|------|
| 注册 `POST /auth/register` | **不要求**口味；可在注册后通过资料接口填写 |
| 改资料 `PUT /user/profile` | 若传了 `tasteTags`，解析后不能为空；推荐前须已有口味 |
| 推荐 `GET /food/recommend` | 必须带 JWT；口味为空则抛「请先完善口味偏好」 |
| 忌口 `dislike_ingredients` | 可选；有则过滤，没有则不过滤 |

## 3. 一次 `GET /food/recommend` 的调用顺序

请求示例：

```http
GET /food/recommend?limit=10
Authorization: Bearer <token>
```

```
DispatcherServlet
  └─ JwtAuthInterceptor.preHandle(request, response, handler)
        ├─ isPublicFoodReviewList(request)          → false（不是 /food/{id}/reviews）
        │     └─ normalizeUri(request)
        ├─ isPublicFoodBrowse(request)              → false（recommend 不在公开列表）
        │     └─ normalizeUri(request)
        ├─ jwtUtil.getHeaderName()
        ├─ jwtUtil.resolveToken(headerValue)
        └─ bindUserFromToken(token, response)
              ├─ jwtUtil.validateToken(token)
              ├─ jwtUtil.getUserId(token)
              ├─ jwtUtil.getRoleId(token)
              └─ UserContext.set(userId, roleId)

  └─ FoodController.recommend(limit)
        ├─ UserContext.getUserId()
        └─ foodService.recommend(userId, limit)
              实现：FoodServiceImpl.recommend   ← 第 4 节逐行展开

  └─ JwtAuthInterceptor.afterCompletion(...)
        └─ UserContext.clear()
```

`/food/recommend` **不会**被 `isPublicFoodBrowse` 放行。没有 Token 时 `preHandle` 调用 `writeUnauthorized`，直接 401，**进不了** `FoodController`。

## 4. `FoodServiceImpl.recommend` 内部逐步调用

方法签名：

```java
public List<FoodRecommendVO> recommend(Long userId, Integer limit)
```

### 4.1 确定返回条数

没有再调别的方法，只做判断：

- `limit == null` 或 `limit < 1` → `topN = DEFAULT_RECOMMEND_LIMIT`（10）
- 否则 `topN = min(limit, MAX_SIZE)`（最大 50）

### 4.2 拉候选菜

```
foodItemMapper.selectOnShelfForRecommend(RECOMMEND_CANDIDATE_CAP)
```

对应 XML：`FoodItemMapper.xml` 里 `id="selectOnShelfForRecommend"`。

SQL 条件：

- `food_item.deleted = 0` 且 `status = 1`（上架）
- `merchant.deleted = 0` 且 `audit_status = 1` 且 `status = 1`（审核通过且营业）
- 排序：`sales_count DESC, avg_score DESC, id DESC`
- `LIMIT 200`

查出的列里包含打分要用的 `taste_tags`、`ingredients`，结果类型是 `FoodItemVO`。

候选为空：直接 `return List.of()`，后面都不跑。

### 4.3 算候选池最大销量 `maxSales`

不调业务方法，用 Stream：

```
candidates.stream()
  .map(FoodItemVO::getSalesCount)
  .filter(销量非空且 > 0)
  .mapToInt(Integer::intValue)
  .max()
  .orElse(1)
```

全是 0 或 null 时，`maxSales = 1`，避免后面除以 0。

### 4.4 读当前用户

```
userId == null                    → throw BizException("请先登录后再获取推荐")
userMapper.selectById(userId)    → User
user == null 或 deleted != 0     → throw BizException("用户不存在")
```

`UserMapper.selectById` 对应 XML：`UserMapper.xml` 的 `selectById`，条件 `deleted = 0`。

### 4.5 解析口味和忌口

```
TagTextUtil.parseTags(user.getTasteTags())           → List<String> userTastes
userTastes 为空                                       → throw BizException("请先完善口味偏好")
TagTextUtil.parseTagSet(user.getDislikeIngredients()) → Set<String> dislikes
```

`parseTagSet` 内部会再调 `parseTags`，然后放进 `LinkedHashSet` 去重。

`parseTags` 做的事：按英文逗号切开，每段 `trim`，丢掉空段。例如 `"辣, 咸鲜,"` → `["辣", "咸鲜"]`。

### 4.6 对每一道候选菜循环

对每个 `FoodItemVO row`：

**① 忌口过滤**

```
TagTextUtil.parseTagSet(row.getIngredients())
TagTextUtil.containsAnyTag(上面的食材集合, dislikes)
```

返回 `true` 则 `continue`，这道菜不进结果。忌口集合为空时 `containsAnyTag` 直接返回 `false`，不过滤。

比较时两边都转成小写（`Locale.ROOT`），所以 `香菜` 和 `香菜` 能对上，大小写不同也能对上。

**② 转成打分用的实体**

```
FoodServiceImpl.toScoringItem(row)   → FoodItem
```

只拷贝：`id`、`foodType`、`tasteTags`、`ingredients`、`avgScore`、`salesCount`。打分不需要店铺名、价格那些字段。

**③ 算原始分**

```
FoodRecommendScorer.scorePersonalized(food, userTastes, maxSales)
```

它内部依次调用（都是 private / 同包静态方法）：

```
scorePersonalized
  ├─ tagHitRate(userTastes, food)
  │     ├─ TagTextUtil.mergeTagSets(food.getTasteTags(), food.getFoodType())
  │     │     └─ 对每一段再调 TagTextUtil.parseTagSet
  │     │           └─ TagTextUtil.parseTags
  │     └─ TagTextUtil.matchedTags(userTastes, foodTags).size()
  │           命中数 / userTastes.size()   → tagPart（0~1）
  ├─ normalizedAvgScore(food.getAvgScore())
  │     avg_score / 5，再夹在 0~1          → scorePart
  └─ normalizedSales(food.getSalesCount(), maxSales)
        sales / maxSales，再夹在 0~1       → salesPart

返回：0.4 * tagPart + 0.3 * scorePart + 0.3 * salesPart
```

菜品标签集 = 菜的 `taste_tags` **加上** `food_type`。例如菜是 `taste_tags=麻辣`、`food_type=川菜`，用户口味是 `麻辣,川菜`，两个都算命中。

**④ 组装返回对象**

```
new FoodRecommendVO()
vo.setFood(stripRecommendOnlyFields(row))
vo.setScore(FoodRecommendScorer.roundScore(rawScore))
vo.setRecommendTags(
    TagTextUtil.joinTags(
        FoodRecommendScorer.matchedRecommendTags(userTastes, food)
    )
)
scored.add(vo)
```

`matchedRecommendTags` 内部：

```
TagTextUtil.mergeTagSets(tasteTags, foodType)
TagTextUtil.matchedTags(userTastes, foodTags)
```

和 `tagHitRate` 用的是同一套命中规则，只是这里要**命中了哪些标签的列表**，不是个数。`joinTags` 用英文逗号拼回去，没有命中则返回 `""`。

`roundScore`：`BigDecimal` 保留 4 位小数，四舍五入。

`stripRecommendOnlyFields`：复制一份 `FoodItemVO` 给前端，**不拷贝** `tasteTags`、`ingredients`（这两列只给打分和忌口用）。

### 4.7 排序并截断

```
scored.sort(Comparator
  .comparing(FoodRecommendVO::getScore, 高分在前)
  .thenComparing(food.salesCount, 销量高在前)
  .thenComparing(food.id, id 大在前))
```

`scored.size() <= topN` 则整表返回，否则 `scored.subList(0, topN)` 再包一层 `new ArrayList`。

## 5. 打分公式（对应函数）

三个子分都先变成 0~1：

| 子分 | 函数 | 公式 |
|------|------|------|
| 标签 | `tagHitRate` | 命中个数 ÷ 用户口味个数 |
| 评分 | `normalizedAvgScore` | `avg_score / 5`，封顶 1 |
| 销量 | `normalizedSales` | `sales_count / maxSales`，封顶 1 |

```
score = 0.4 × tagPart + 0.3 × scorePart + 0.3 × salesPart
```

常量在 `FoodRecommendScorer`：`WEIGHT_TAG`、`WEIGHT_SCORE`、`WEIGHT_SALES`。

手算例子：用户口味 `辣,咸鲜`（2 个）。某菜 `taste_tags=辣`、`food_type=盖饭`，只命中「辣」。`tagPart = 1/2 = 0.5`。均分 4.5 → `scorePart = 0.9`。销量 80，池子最大 200 → `salesPart = 0.4`。

```
score = 0.4×0.5 + 0.3×0.9 + 0.3×0.4 = 0.20 + 0.27 + 0.12 = 0.59
```

`roundScore` 之后响应里大约是 `0.5900`。`recommendTags` 为 `"辣"`。

## 6. 口味数据是怎么写进库的（推荐之前）

推荐本身不改用户。口味来自注册或改资料。

### 6.1 注册

注册不写口味。用户通过 **6.2 改资料** 设置 `tasteTags` 后再调推荐。

### 6.2 改资料

```
PUT /user/profile
  UserController → UserService.updateCurrentProfile
    └─ UserServiceImpl.updateCurrentProfile(dto)
          ├─ requireCurrentUser()
          │     ├─ UserContext.getUserId()
          │     └─ userMapper.selectById(userId)
          ├─ buildProfilePatch(id, dto)
          │     若 dto.tasteTags != null：
          │       TagTextUtil.parseTags
          │       TagTextUtil.joinTags
          │       结果为空 → 「口味偏好不能为空」
          │       否则 patch.setTasteTags(...)
          │     若 dto.dislikeIngredients != null：
          │       patch.setDislikeIngredients(...)
          ├─ hasProfilePatch(patch)  全空则不写库
          ├─ userMapper.updateById(patch)
          │     XML 动态 <if>，只有非 null 列才 SET
          └─ userMapper.selectById → toProfileVo
```

  }

| `recommendTags` | `TagTextUtil.joinTags(FoodRecommendScorer.matchedRecommendTags(...))` |

## 8. 异常分别在哪抛

| 现象 | 函数 |
|------|------|
| 401「未登录或 Token 缺失」 | `JwtAuthInterceptor.preHandle` → `writeUnauthorized` |
| 401「Token 无效或已过期」 | `bindUserFromToken` → `writeUnauthorized` |
| 「请先登录后再获取推荐」 | `FoodServiceImpl.recommend`（`userId == null`，正常带 Token 时不会发生） |
| 「用户不存在」 | `FoodServiceImpl.recommend` |
| 「请先完善口味偏好」 | `FoodServiceImpl.recommend`（`parseTags` 结果为空） |
| 候选为空 | 不抛异常，返回 `[]` |
| 忌口把菜滤光 | 不抛异常，返回 `[]` 或更短的列表 |

## 9. 自测时看什么

1. 注册 body 带 `"tasteTags": "辣,咸鲜"`，库里 `sys_user.taste_tags` 有值。  
2. 登录拿 token，`GET /food/recommend?limit=10` 带 `Authorization`。  
3. 看 `recommendTags` 是否是用户口味的子集。  
4. `PUT /user/profile` 设 `"dislikeIngredients": "香菜"`，含该食材的菜应从列表消失。  
5. 不带 Token 调推荐，应 401，而不是空列表。

库表列来自 `sql/patch_recommend_tags.sql`：`sys_user.taste_tags`、`sys_user.dislike_ingredients`、`food_item.taste_tags`、`food_item.ingredients`。没执行脚本时，`selectOnShelfForRecommend` 会报未知列。
